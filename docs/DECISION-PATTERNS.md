# Patterns in the builder's misses

Analysis of the misses in `DECISION-LOG.md`, which holds only the raw entries. The builder reads this file before predicting Peter's answer or deciding whether to ask, and adds a pattern when one shows in the log. The rates themselves come from `python3 ~/.claude/skills/decision-log/stats.py docs/DECISION-LOG.md`.

- **Overconfidence.** In the 2026-10-02 predictions, at 75–80 % confidence the builder scored 2.5 of 4; at 55–65 %, 2.5 of 5; at 40 %, 0 of 1: about 15 points overconfident.
- **Hard lines read as conditions.** Where Peter holds a rule without exceptions ("never change providers", "never decrypt users' content"), the prediction was a yes with conditions.
- **A cost emergency generalised into a cost mandate.** The 2026-09-12 digest incident was a fix for runaway spend, not a standing wish to cut cost. In this phase he puts product quality first.
- **The builder's own proposals used as evidence of his view.** "Consenting alpha users" came from the builder's triage note, not from him.
- **Assumed constraints instead of checked ones.** A social reason was guessed for not contacting reporters; the real limit was that no channel exists.
- **Urgency judged for a later phase.** A privacy cleanup was predicted as urgent although, before the Beta, the data at stake is mostly Peter's own and test data; he lets it expire and would act at once only with Beta users (2026-10-08, Sentry).
- **User-facing text written by the builder gets corrected.** On 2026-10-09 Peter changed the home navigation word, the name and the line of the Glean card (twice), and the account-deletion text in the terms ("hidden" was the implementation's word; the backups sentence was "not at all clear"). The drafts described the mechanism or the implementation; he wants a short line in the user's words. Offer two or three candidates and a recommendation instead of one finished text, and write what happens to the user. Briefs show the same: on 2026-10-20 #414's smaller choices, stated as mechanism without the number or what the user sees, drew "what is the full amount" and "why?", and "facts a user adds count as true" was "imprecise".
- **A recommendation to defer gets "do it now".** Peter said "now that we're talking about it, add them pls" to a follow-up issue for a small addition to the same feature (#471, 2026-10-09), and asked "can we do it now?" about a maintenance task the builder had put after the Beta-critical work. When the extra work is small and belongs to the feature under discussion, predict "now". The opposite holds for a change with open product questions and for a lasting commitment: Peter deferred #518's memory cleanup (2026-10-16) and storing outside images on Loore's server ("It needs a longer term decision", 2026-10-20), both recommended for now.
- **Capabilities limited to admins or the server become capabilities for every user.** The Glean model choice was predicted as admin-only (70 %) and as server-chosen for everyone else (75 %); Peter wanted the same picker for everyone whitelisted. The provider rule was read as "the user can't choose" when it means "Loore doesn't change a provider without the user's knowledge". Predict that users keep their choices and that restrictions apply to Loore's own switching.
- **Quality-first applied where the feature runs on every request.** The builder set Sonnet 5.5 as the default Glean model; Peter chose Haiku 5.5. The early-phase "best product first" holds for what a user does rarely; for per-request features with an evaluated cheaper model, predict the cheaper default.
- **Marked ready on reviews and unit tests, rejected on first use.** Peter tried Glean locally on 2026-10-09 and said "overall, this feature seems untested". The builders had passed code reviews and unit tests, and nobody had used the feature in a browser. The first use found six problems: a voice flow that looked like a batch job, rerun buttons on a synchronous flow, a "Back to Home" link, a missing button on the Glean entry, a native tooltip and an action that was hard to find. Before a user-facing feature is marked ready, use it end to end in a browser and keep screenshots. Again on 2026-10-16: profile chapters (#517) passed tests that wrote chapter data straight into the database and showed no chapters on a real generated profile, and a two-line iPhone change (#520) was offered after a parse check alone. Check a feature on real content of the kind it is for, and run app changes in the app.
- **A "Needs Peter" item in a PR body that never reaches a brief defaults silently.** The #415 question "does a deleted writing stay visible for 30 days?" was listed in the PR, never asked, and resolved as "as built"; Peter's model was "a soft-delete of everything immediately" with a restore. Every Needs-Peter item goes into the next brief, or is decided by the builder and logged as an escalation entry.
- **Claims passed on without a check.** On 2026-10-20 six claims reached Peter unchecked, most of them from subagents' reports: a brief's example named an Account-page field that no screen has; a reply said that nothing shows the old profile description, from a search of the web app alone, while the server-rendered public page still showed it; the default model was read from the code's fallback instead of the production setting; one export's share of user text was presented as typical; and twice, how prod builds the profile was described without checking it (that chunks collect facts and only merges read between the lines; that the final merge mixes versions of very different coverage). Before a claim about the product goes into a brief or a reply, check it where it is true: the screen, the rendered page, the production setting, the pipeline's code. The same holds for experiment results: on 2026-10-21 two first places in separate evaluations, scored on different lists of facts, were stated as a tie between them ("did it?").
- **Peter's words taken to exclude more than he meant.** On 2026-10-20 "no way to weigh vibes" was read as ruling out every merge of unequal pieces; his next design asked to test one, with an instruction to weigh coverage. On 2026-10-21 "merged using the A design" was read as the single merge only, which dropped the two-level arm of the scale test he meant. On 2026-10-22 "the budget for tonight is $10" was read as the night's total, where he meant $10 on top of the tests already approved. Each reading dropped something he had proposed or approved. When a sentence of his can be read as excluding something already on the table, keep it in, or ask in one line.
- **New prompt rules where the existing wiring would do.** For #414 the builder proposed prompt instructions twice (keep the user's words and add a marked observation; protect an edit until later entries contradict it). Peter's answer was the existing version chain and the current update prompt: "This will require no prompt change vs current prod, we just need to make sure the wiring works". He also wanted the user's version to reach the model as what the user said, with "no special treatment", and the design he accepted for rebuilds (merge an edit at its date) reuses the existing integration step. Before proposing a prompt rule, check what the pipeline already gives the model.
